# Explicit tunnel startup

The shipped base service has no `--tunnel-config`; TUN is OFF. Merely creating a configuration file does not enable it. The Ansible profile stays public configuration and carries no invitation, Relay capability, TLS private key or automatically applied service override.

`delivery/consolecrypt-agent-tunnel.conf.example` is a noninstalled example for an operator-reviewed systemd drop-in. It preserves the base entrypoint and arguments, adds the literal trusted path `/etc/consolecrypt-agent/tunnel.json`, and adds one documentation-only address `203.0.113.10` to the existing loopback-only allowlist. Replace that address with the approved numeric Relay endpoint before installation. The base `IPAddressDeny=any`, loopback allowance, user, filesystem protections and resource bounds remain in force. Do not replace the policy with an all-address allowance. This repository change does not install the example, reload systemd or restart/enable a service.

The example extends only the outer stop grace to30 seconds for the sequential bounded sampler, carrier, Reader and worker owner joins. This gives cleanup time; it never extends a Relay/Node/Reader authorization TTL. The OFF base service remains unchanged. Its `TasksMax=16` remains in force; an enabled whole-startup gate must measure the actual process/thread count against that limit before any deployment claim.

Before such an explicit action, independently provision the Node/Actor, current owner pin, owner-approved policy and distinct existing custody, checkpoint, Node and audit directories. Configure them within the service's already writable StateDirectory roots without nested/overlapping namespaces; the configuration validator rejects overlap. Provision the matching server certificate/private key and public client/Relay CA inputs. State is not adopted, permissions are not repaired, keys are not generated and grants are not minted at startup. No secret configuration template is supplied.

`TunnelConfig` requires absolute trusted regular input paths, the exact identity executable hash, private owned state directories and mode0600 private TLS key and Relay-offer file. Its identity/store/checkpoint/owner-pin configuration must match the existing SQLite custody gate. The private Relay-offer file contains exactly `origin`, `slotId`, `dialIp`, `capability`, `expiresAt`, `idleSeconds`, and `maxCiphertextBytes`. It is an explicitly supplied one-use transport witness with a live original expiry of at most300 seconds; it grants no Node permission. The actual carrier validates its endpoint/limits, and inner TLS plus the existing Actor independently admit the operation. Do not place this file or any private TLS key in Git, a public profile or inventory.

One process start makes one outbound attempt, with no automatic capability discovery, reconnect or lease renewal. Ordinary service recovery never creates a replacement Relay offer or Node authorization. Shutdown cancels and joins owned carrier/worker resources; uncertain cleanup remains a failure. `--once` validates explicit configuration but returns its heartbeat before starting the listener, worker or tunnel. The default/OFF and negative startup tests do not establish a deployed systemd installation or an end-to-end enabled startup gate.
