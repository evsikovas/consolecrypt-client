# Нативная проверка и подтверждение задания

Контракт реализованного интерактивного запуска в текущих исходниках.
Проверка исходников и стендов не означает выпуск нового установщика.
Постоянная служба имеет отдельное согласование, описанное ниже.

## Данные подтверждения

UI передаёт ID проекта, Runner, выбранных сохранённых хостов, путь playbook,
mode и структурированные параметры. Никакого входного signature/manifest API
для модели или Flutter нет. AppCore сам строит revision, frozen inventory,
реальные проверенные SSH-маршруты, policy и времена; сохраняет приватный
review с непрозрачным одноразовым ID. Подтверждение принимает только этот ID.

Review относится к одному профилю и поколению unlock, имеет TTL и собственные
заранее аутентифицированные target sessions. Он не хранит Arc<Unlocked>, общий
resolver или plaintext приватных ключей. Изменение проекта, маршрута,
подготовленного окружения, параметров или выбранных целей требует новой
проверки. Перед подтверждением повторяется проверка sharing маршрутов.

На Windows целевой TCP-origin расположен в выбранном WSL; remote Runner
использует собственный проверенный SSH-маршрут. Proxy/backend без подходящего
адаптера отклоняется явно. Validation не получает target socket или credentials.

## Дополнительное подтверждение production

Для интерактивного production-запуска применяется политика
`ownerConfirmationVaultPassphraseV1`: после просмотра карточки владелец отдельно
подтверждает действие парольной фразой текущего хранилища. Это повторное
подтверждение владельцем, а не согласование вторым человеком. Windows Hello,
сохранённый presence token и ответ ИИ не заменяют парольную фразу этой политики.

AppCore сохраняет точный manifest, Job ID, digest и исходные времена ещё до
подтверждения. Успешная проверка парольной фразы не пересоздаёт manifest и не
продлевает срок. Подписанное подтверждение относится только к его digest и
исходному signer. Проверки Native и Python Runner обязательны: обычная кнопка
подтверждения, изменение manifest, другой профиль или устаревшее unlock-поколение
не дают production-разрешения. Повторное использование принятого review
отклоняется. Неверную парольную фразу можно исправить только в пределах срока
того же исходного review.

Если Runner или клиент не поддерживает эту политику, production-запуск
недоступен. Автономные Service/Node producer не получают эту интерактивную
возможность и продолжают отклонять production-задачи.

## Хеши Python и Rust

JSON-числа могут иметь различное текстовое представление (`1e-07` и `1e-7`,
`1e+20` и `1e20`). Нельзя просто хешировать независимые сериализации и считать
различные значения или форматы взаимозаменяемыми.

Helper возвращает приватные response-only input witnesses: точные UTF-8 JSON
байты, которые он хешировал, и digest. Rust строгим parser отклоняет duplicate
keys/nonfinite/depth overflow, сравнивает весь parsed value с собственными
исходными данными и независимо вычисляет SHA-256 этих байтов. Digest также
сверяется с report. Witnesses не сохраняются в validation.json, не выводятся
в diagnostic Debug и не передаются в публичную карточку review.

`ValidationProof` дополнительно проверяет revision/environment/playbook,
digest точного массива целей, порядок syntax/lint, результаты и ограничения
вывода. `valid:true` без согласованных успешных проверок отклоняется.
`VerifiedValidation` имеет закрытые поля и создаётся только этим verifier.
Его данные сами по себе не выдают полномочия: native signing требует реального
подтверждения review и актуальных локально выведенных прав.

Проверены unit tamper cases и настоящие remote/WSL jobs с дробными параметрами.
Canonicalization подписанного JobManifest при этом не менялась; алгоритм
параметров helper остаётся прежним, с независимой проверкой его входных байтов.

## Очередь интерактивного клиента

AppCore должен принимать подтверждённые задания в собственную durable очередь
и передавать `accept_job` helper только при получении локальных блокировок
Runner/Host ID. Это позволяет сериализовать цели между приватными helper без
выдачи credentials через неподтверждённые задания. Один Runner исполняет одно
интерактивное задание; check тоже может изменять сервер через check_mode:false.

В очередь сохраняется Job ID и связь с manifest до отправки запроса helper.
Потеря acknowledgement разрешается запросом того же ID, без нового исполнения.
Истёкшее согласование не продлевается автоматически. Очередь, не принятая
helper до vault lock, ждёт unlock или отменяется по policy; уже принятое
задание может продолжаться до ранее подписанного TTL.

Native coordinator удерживает target fences до наблюдения известного итога.
Unknown не освобождает их как доказанно успешное завершение: требуется явная
сверка/подтверждение пользователем. После рестарта незавершённые durable
записи восстанавливаются консервативно, не переотправляются как новые jobs.
Выход/смена профиля требуют выбора wait либо cancel-and-close; другие
терминалы, WSL и пользовательские контейнеры не завершаются.

Постоянная служба, межустройственные identities/delegation, общая pool lease
и fencing относятся к E3. Независимые внешние Ansible-контроллеры локальная
очередь ConsoleCrypt не координирует.

## События, снимки и восстановление интерактивной сессии

`job_events` разрешён только для задания, уже сохранённого в текущем SQLCipher
профиле. Helper сверяет tenant/Runner, клиент дополнительно сверяет Job ID,
manifest digest и непрерывный sequence/cursor каждой страницы. После переподключения
читается тот же журнал; запрос истории не принимает задание повторно. Пустой
набор разрешённых проектов/целей допускает чтение собственной истории, но
не даёт права исполнить новый manifest.

Журнал ограничен 50 МиБ на job и 1 ГиБ суммарно. Индекс смещений через каждые
128 записей восстанавливается из fsynced журнала при открытии, затем поздний
cursor читает хвост вместо полного перечитывания на каждом poll. UI держит не
более 50 событий/1 МиБ, поздние ответы от старого unlock не возвращают текст.
Эти лимиты не заменяют ещё не поставленную retention/export политику.

## Явный повтор из истории

«Подготовить новый запуск» открывает новый setup, не переотправляет старый
manifest. По умолчанию снова выбран check mode; Runner, цели и переменные
пользователь выбирает заново. Предыдущий результат остаётся доступен рядом,
интерфейс предупреждает об уже применённых и возможных частичных изменениях.
Автоматического выбора «неуспешных хостов» и универсального resume нет.

Native принимает `retry_of` только для завершённой записи текущего профиля,
того же проекта и playbook, с явно выбранным подмножеством прежних Host ID.
Активный/unknown job повторять нельзя. Для unknown сначала требуется
отдельная сверка и явное подтверждение неопределённого результата.

Новый review замораживает ID и manifest digest родителя. При durable admission
в той же транзакции повторно проверяются родитель и его связь с текущим review.
Пропавшая, изменённая либо будущая запись не превращается в обычный запуск.
Новые revision/environment/parameters проверяются обычным gate; создаются
новые review/job/nonce/signature. Старая подпись не используется. Связь
`retry_origin` хранится в SQLCipher истории; она не расширяет полномочия и
не является заменой проверок нового подписанного manifest.

`revision.json` хранит точный UUID частного снимка и его digest до durable
подтверждения приёма job. Равные по содержимому снимки с разными UUID можно
освободить независимо. Для старой/неполной записи без UUID остаётся более
строгая привязка по digest: неизвестную ссылку нельзя угадать и удалить.

## Ansible-группы проекта

Project metadata содержит отдельный versioned `inventory.groups` со стабильными
Host ID. Один хост допускается в нескольких группах; его папка, credentials и
сохранённые маршруты не изменяются. Названия all/ungrouped/_meta зарезервированы.
Документ ограничен 128 КиБ, 64 группами и 10 000 memberships; повторные ключи,
Host ID и неизвестная схема отклоняются. Сохранение проверяет существование
хостов, ожидаемую revision и исходный unlock/profile.

Настройки пока device-local в SQLCipher. Это не реализация внешнего
INI/YAML inventory, merge/conflict resolution или encrypted sync. Будущая схема
сохраняется без перезаписи и делает проект недоступным для изменения/запуска.

Перед validation native строит группы только из пересечения memberships и
фактически выбранных целей с подготовленными SSH sessions. Остальные Host ID
не получают ни alias в runtime inventory, ни credentials. Полный inventory
digest проверяется обычным validation proof и входит в новый подписанный job.
Review и история показывают замороженные группы. Изменение состава повышает
revision проекта и отменяет возможность подтвердить прежний review.

Редактор групп сохраняется отдельно от содержимого открытого YAML. Закрытие
или блокировка не превращает поздний ответ metadata в восстановленный экран.
При удалённом/недоступном Host ID UI позволяет явно убрать membership; состав
не теряется молча. Native gate остаётся обязательным независимо от checkbox.

## Предложение Ansible через ИИ

Предложение документа отделено от shell execution gate и от native job review.
Контракт `PreparedAnsibleRequest` не содержит filesystem/SSH/credential API.
Пользователь выбирает провайдера и задачу, отдельно включает и редактирует
контекст открытого файла. AppCore не добавляет hosts, terminal, RAG или facts.
Sanitizer формирует точные сообщения; native preview показывает их до первого
chat-запроса. Явное согласие потребляет одноразовый ID (TTL 10 минут), отправляет
один запрос выбранному провайдеру, без fallback и автоматических repair/run циклов.

Typed JSON schema ограничивает ответ одним относительным YAML файлом, объёмом,
переменными/зависимостями/изменениями/проверками/замечаниями. Неизвестные и
повторные поля, подмена пути, tools и обрезанный ответ отклоняются. Локальные
эвристики только добавляют предупреждения; они не сертифицируют безопасность
плейбука и не заменяют isolated syntax/lint и отдельное согласование целей.

UI показывает diff и вставляет результат только в несохранённый редактор.
Сохранение сохраняет expected SHA исходного файла. Оно не запускает Ansible.
Lock/close/cancel отзывают HTTP запрос; изменённый provider/API-key revision
отзывает preview и активную генерацию. Контекст, provider и запрос не
сериализуются в sync/vault. До поставки encrypted draft persistence черновик
существует только в памяти текущего unlock. Встроенная модель удерживается
device-local lease на время preview/inference; ошибка не переключает её на API.

Проверки с синтетическим HTTP-провайдером подтверждают фактически отправленный
текст, одноразовость и отмену ожидающего ответа. Это не измерение качества
реальных моделей: фиксированные AI-11 сценарии остаются отдельной приёмкой.
